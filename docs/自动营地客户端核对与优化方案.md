# 自动营地客户端核对与优化方案

分析日期：2026-10-14。下文保留方案提出时的客户端证据。用户随后确认宠物与据点共享成功次数上限并授权实现；最终行为与验证说明见[营地共享成功次数与领奖](营地宠物三次胜利.md)。

实施说明：默认补齐共享3次成功，已完成的据点/宠物成功均计入，不额外追加三场宠物。采用配置化次数与时段、资格、镜像、isWin、每场查询、战报超时对账和任务领奖；特权自动打满5胜仍是可选后续功能。

## 推荐方案

1. 入口加载当前官方配置，按服务端时间核对赛季、挑战阶段、报名、参战资格及特权，跳过原因明确记录。出手上限从配置读取；默认目标保持用户要求的3胜，特权5胜可作为后续可选项。
2. 保留低战力据点优先和连续3次失败切宠物策略。目标排序补充实时难度；失败后避开同一角色/镜像/难度组合，候选失效刷新重选。请求补传targetIsMirror，保留useItem=false和当前攻击阵容。
3. 普通和宠物使用battleData.result.isWin判定战斗，并在每场后club_getinfo对账。原始字段省略时，仅依照已核实协议默认值归一化，不能把整个空响应当作失败或成功。
4. 切宠物后按用户要求以3次宠物胜利为目标，但每场重查官方成功上限、任务进度和当日战报；已达服务器上限时停止，不能盲发第三场。尚不能确认普通与宠物是否共享aSuccessCnt，需要一份当前宠物响应和前后club_getinfo核实。若共享，先前据点已有胜利时可能不能再获得额外3次宠物胜利，应明确记录这个约束。
5. 运行前利用当日战报确认已有宠物胜利，重复运行补缺而非重新打3场；必须核实records覆盖范围和created单位，记录不全时不宣称已恢复完整当日次数。宠物超时先查询状态和战报，有可靠新增结果才继续，无法唯一确认则停止。
6. 战斗结束后查询最新营地任务，按当前配置逐档领取已达标未领项，查询taskClaimedMap确认。配置包含已废弃任务和按难度的俱乐部任务，不能将“3场宠物”直接等同于所有每日任务已完成。日志分开显示据点胜利、宠物胜利、当日任务达标和奖励已领取。
7. 增量响应按账号合并；保留串行账号、连接池、停止及跨日保护，新增跨22点保护。针对服务器13000070按官方行为刷新目标和阵容，确认尚未发生攻击后才重选，不盲重发。

## 实施顺序与验证

第一阶段：开放时段、资格、配置次数、镜像参数、isWin和每场查询，纠正确定的客户端差异。
第二阶段：战报恢复/超时对账及任务领奖。先核实当前真实响应，尤其宠物胜利是否改变aSuccessCnt、taskProgress和records覆盖范围；未核实之前不假设存在独立宠物每日计数字段。
第三阶段：按难度优化目标选择、缩小阵容查询次数、可选特权5胜目标。缓存仅限账号本轮并绑定角色/镜像/难度，刷新失效后重新取阵容。

实现时添加10/15次上限、3/5成功上限、10点/22点边界、报名与参战资格、镜像、isWin与血量不一致、目标被别人击败、难度升级、宠物计数变化、战报不足、超时无法唯一对账、逐档领奖及跨日回归；本轮只读分析未运行业务测试。

更新游戏时重新请求manifest及配置版本，核对上述稳定方法名和配置表，不写死本次bundle哈希。
