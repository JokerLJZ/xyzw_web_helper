## 官方前置判断

`canOneLevelUp` 先排除缺失武将及客户端临时武将，遍历四件装备选最低等级的一件。如果它已达到 `ROLE.lord.level`，或者 `EquipmentInfo.isMaxLevel` 为真，返回 0，不发送升级请求。

`isMaxLevel` 取 `ConstantConf.equipmentOrder` 最后一项。普通升级由 `judgeLevelUpNum` 按 50、10、5、1 检查精铁消耗、主公等级和当前装备阶段上限；最低装备恰好处于阶段上限且未最终满级时，另行检查一级消耗，允许一键请求。因此不能把“达到当前阶段上限”统一视为无法升级。

`batchUpgradeLevel` 对返回 0 的情况只显示提示；返回 -1 引导获取精铁；返回 1 才发送请求。成功时重置装备颜色显示并触发刷新。真实服务端的完整选择/消耗算法不在客户端，本次未在线验证。

用户日志证明本次升级请求收到 `500060 - 没有可升级的装备`。该响应应按本功能的正常无操作结果处理；不能仅凭该日志断言三个账号均因主公等级受限，也不能改称“四件装备均已满级”。

## 项目问题与建议实现

`src/utils/batch/tasksItem.js` 的 `batchUpgradeEquipment` 目前只判断四件装备是否到 4000 级，以及精铁是否够最低一级消耗，缺少主公等级限制；所有异常统一标记 failed。

1. **最小修复**：仅在 `equipment_batchupgradelevel` 请求周围捕获已确认的 500060，将账号标记 completed，信息日志显示“吕布当前没有可升级的装备，跳过升级”；不记升级成功、不自动重试，继续后续账号。角色查询、连接阶段的错误不得被这条规则吞掉。
2. **补齐前置判断**：使用该账号刚查询的 `role.lord.level` 和最低装备等级，达到主公等级上限时直接正常跳过；保留最终满级和精铁不足判断。若关键字段缺失或无效，不按 0 等级、满级等默认值猜测，保留明确的数据异常。阶段突破按官方分支处理，不能简单过滤所有达到阶段上限的装备。
3. **错误识别**：WebSocket 两处响应拒绝目前只构造包含错误码的 Error 文本。建议保留可读文本并附加 `code`、`cmd` 字段，业务按数值或数字字符串 500060 判断；兼容旧错误文本时严格匹配错误码边界，避免宽泛地忽略“升级”或“没有”相关异常。其他业务错误、超时及断线继续失败；不在全局把 500060 转成成功。
4. **成功日志**：只在升级请求成功时记录已升级；前置跳过和服务端无可升级分别记录原因，避免把未发生的升级计为成功操作。
