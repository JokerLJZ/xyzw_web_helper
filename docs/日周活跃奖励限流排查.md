## 项目行为

| 位置 | 观察结果 |
| --- | --- |
| dailyTaskRunner.js：积分领取入口、活跃奖励入口 | 分阶段集中 refreshServerRole；没有每档领奖前重复查询 |
| refreshServerRole | sendGetRoleInfo(tokenId, {}, 2)，禁用其内部重试；响应后等待 commandDelay |
| executeGameCommand | 等响应后等待可调 commandDelay；默认500ms，没有领奖专用最低间隔 |
| 日/周活跃奖励循环 | 顺序等待每档领奖；一档抛错会跳出当前整组 |
| sendRequest / throwIfInterrupted | 200400、12400000 会记为 transportFailure，阻止后续操作，200400因此终止本轮 |
| xyzwWebSocket.js | 发送队列50ms轮询；保证队列顺序，未提供账号所有请求的安全最低间隔 |
| 最终核对 | 统计仍可领取奖励，没有在本轮补领；错误提前退出也可能到不了最终核对 |

结论：查询会贡献请求量，但现有代码证据不支持“每档多次查询”是根因。直接缺口是最低间隔不足与限流后整轮退出；真实触发请求及服务端阈值仍需运行日志验证。

## 已实现方案

1. 日常任务积分查询/领取、日活与周活领奖统一账号串行节奏，相关请求从上次响应结束后至少等待1秒；用户配置更长时采用更长值。1秒是用户确认的初始值，不是官方阈值。
2. 保留积分前和活跃奖励前必要的集中查询，日周两组共用最新快照，最终集中核对；不新增每档常态查询。
3. 仅在该领奖流程内处理明确200400：冷却1.5秒，再按安全间隔读取服务器状态；确认仍可领取才重试一次。已经领取则跳过；再次限流停止补领并报告待核对项。其他任务错误策略不全局放宽。
4. 超时先核对状态，确认已领取则继续，未领取则停止、不盲目重发。断线、查询失败、跨日均停止；服务器提供weekTime时同时核对周重置。无法确认就报告待核对。
5. 日志区分请求成功和服务器标记确认，并记录具体查询/领奖指令、rewardId、错误码与请求间隔；最终明确列出剩余日/周奖励。
6. 新增13项回归覆盖低延迟配置、较长用户配置、日周切换、集中查询次数、积分/日/周首档限流恢复、冷却后已领不重发、再次限流、超时、断线、查询失败和跨日/周停止。

实现位于`src/utils/dailyTaskRunner.js`，测试位于`test/dailyTaskRunner.test.js`。最低间隔从积分领取阶段起施加到该runner后续请求；普通领奖不增加查询，异常限流或超时才查询核对。未修改底层WebSocket全局发送策略。
