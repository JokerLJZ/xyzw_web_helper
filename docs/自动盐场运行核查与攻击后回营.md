## 核查结论与本次修改

原有正常流程为进场 → 复制/核对阵容 → 出战 → 最近合法地块 → 预算内加速 → 到达后重新核对 → 一次攻击 → 本人及battleId对应结算。以下问题已修改：

1. **攻击后原地结束**：新增结算后的回营阶段。先保存独立的attackCompleted，再刷新本账号战场；读取本军团position并检查合法路线，使用`war_startmarch`行军并持续加速。本人idle、位置等于大本营且本人march消失，才写入completed。攻击与回营分别使用设置的最长等待，去程、回营均按最快模式执行，不受旧版一次/20金砖设置限制；低于可加速时间门槛或余额不足后自然到达。
2. **行军超时后永久待核实**：旧记录停在march且没有活动行军时，原实现不检查实际位置。现在本人已经idle且到达记录目标可继续，不重发去程。
3. **途中加入多人队伍**：原实现主要在入口和补查时核对单人条件，通知更新队伍后可能继续发送。现在每次执行检查、等待和写操作前都重新检查多人队伍/组队冷却；发现变化即停止。
4. **省略hP导致有效结算误判取消**：只对攻城结束通知恢复当前协议默认hP=0，保留显式负值取消语义；不对每次战场增量重复添加默认状态。

回营超时或请求失败保留已攻击和回营阶段，重跑先查询：已到家则完成、已有本次回营行军则继续等待、结果仍不明则pending，不重复攻击或回营。死亡、复活、战斗状态、其他行军、路线不可达或多人队伍不强行回营，不自动复活。用户停止后不再发送后续动作；已经发出的行军仍由游戏继续。

兼容限制：旧版本已经写成completed的场次仍按旧完成记录跳过，不追溯移动这些账号。攻击已发起但结算通知丢失且无法确认结果时仍保持pending，不凭空认为攻击成功。当前实现仍只支持已适配普通盐场地图；回营路线因战场动态变化可能被服务端拒绝，错误保留待核实记录。

## 全程最快加速（同日追加）

用户要求所有行程加速到最快。默认`accelerateAll=true`，包含旧设置未带新字段时；去程和返回大本营共用连续加速器，界面移除一次/预算控件。旧预算字段仅供显式`accelerateAll=false`的兼容调用使用，默认批量、定时均为最快模式。

当前`LegionWarModule.sendSpeedUp` → `WarService.speedUp({battlefieldId,marchId})`；War注册表注册`speedUp`并用battlefieldId作hint，指令为`war_speedup`。当前普通地图费用取战场SpeedCost优先、配置回退；仅单人队伍，所以不乘额外队员人数。每次加速前独立查询本账号金砖，检查最新本人march/state/endTime；两次请求至少间隔2秒（按上次响应后计时），到客户端MoveTimeLowerLimit门槛后不再发送。不能将“最快”理解为绕过服务端最低行军时间或立即传送。

每次加速发送前持久化费用及speedPending；返回后要求本人行军endTime缩短或该行军结束，缺少更新时只读补查一次，仍无变化停止。超时或效果不明不会重发该次付费；重入可自然等待原行军结束，再清理该行军的不确定标记。新增回归覆盖旧预算不限制最快模式、去回程各多次加速、2秒间隔、余额耗尽、效果未确认停止。未进行真实账号消耗验证。
