## 原因及边界

正常每层2次战斗请求+3次getinfo，另可能3次无条件任务领奖；N层基础约5N+1个塔请求，尚未计章节和失败重试。readyfight与fight之间没有应用层间隔，任务领奖仅隔200ms，多账号并发会放大突发密度。异常统一等待1秒重试，不区分限频、超时或业务失败；战斗真实完成后若领奖出错也可能被混为战斗失败。连续3次失败break之后仍可显示completed。

这些是已确认的请求冗余与处理缺陷，但未取得用户本次错误码、失败指令和服务器限频规则，不能断定唯一触发点或声称知道服务器阈值。

## 拟修改流程

每账号保持一次连接、独立状态；入口读取塔/合成/必要领奖信息 → 补领当前已达标奖励和免费钥匙 → 按配置爬塔、章末领奖 → 爬塔结束统一检查新达标的全部钥匙来源 → 使用钥匙 → 领累计使用及合成奖励 → 合成 → 再查新达标奖励；有新增钥匙则继续使用与合成，直到无新增资源/无合成进展/主动停止/达到合理安全上限。

不自动购买、充值、邀请、发消息；仅领取账号现有资格已达标的奖励。俱乐部特权属于增益，不当作钥匙奖励盲领。已购待发钥匙及通行证仅在明确可领取时处理。各阶段只重复检查可能随该阶段变化的来源，避免每次开钥匙全量查询。

## 降频与状态

1. 删除循环开始和额外能量刷新，复用最新完整状态，默认战后只查询一次；若响应包含已确认完整必要字段，可合并增量减少查询，但不在本次调查中假定响应字段。超时或状态不足才额外核对。
2. 每账号统一请求间隔，建议初始500ms、战斗轮次至少3秒；多账号按现有maxActive限制，启动错峰。这是保守初始参数，不是服务器阈值，需根据实测调整。
3. 明确200400限频时冷却6/12/24秒再核对，设有限重试；超时写请求先查结果，不能直接重发消费或战斗；仍无法确认则记录失败，不假装完成。
4. 只在任务达标且未领时请求；领取返回增量合并到该账号状态，失败记录来源和错误码，不再catch吞掉后显示成功。
5. 阵容只必要时切换，在finally尽力恢复；停止、真实失败和完成分别记录。

## 用户确认后的实施范围

不实施上文降频建议：不增加500ms统一请求间隔、3秒战斗轮次、错峰、并发限制或6/12/24秒退避。保留原有战后1500ms、用钥匙500ms、手动合成300ms、自动合成1500ms及合成轮次500ms等待。200400直接记录错误，不盲目重发；一键流程核对最新状态后仍可处理独立钥匙阶段，账号最终保留失败原因。
