## 礼包领取与开放条件的证据

| 环节 | 可复查调用链与行为 |
| --- | --- |
| 打开玩具 | 房间/武将入口 → `WeaponModule.sendGetWeaponInfo` → `LordWeaponService.get({})`；这是查询，不是领取礼包 |
| 礼包按钮 | `WeaponInfoDialog` / `WeaponInfoDialogV2._onClickReward` → `WeaponModule.sendClaimOpenReward` → `LordWeaponService.claimOpenReward({})` |
| 是否可领 | `WeaponModule.isOpenRewardExist` 检查玩具模块开放和 `role.statistics["lord:weapon:claim:open:reward"] <= 0`；空Map中的缺省记录按0处理 |
| 礼包奖励 | `ConstantConf.WeaponOpenReward` 为道具1026（扳手）500个，是开放礼包，不是每日礼包 |
| 星级统计 | `WeaponPassiveSkillToolTip.curStars` 遍历 `role.battleTeam`，按每名上阵武将的 `role.heroes[heroId].star` 相加 |
| 解锁说明 | `C2_Weapon_CONST4`：“上阵武将达到{0}星后永久解锁”；`WeaponConf[2].passiveSkill=[5,6,7,8]`，`passiveSkillUnlock=[80,100,110,130]` |
| 是否还需点击激活 | 两版界面的锁定被动点击不可选中，信息按钮仅打开说明；完整LordWeapon注册列表中没有独立的被动激活方法。不能把玩具本身的 `unlock` 当成被动解锁指令 |
| 装配与生效 | 官方 `LORD_WEAPOM_RULE` 说明被动解锁后永久生效，但需装配该玩具。界面主动/被动升级使用 `role.lordWeaponId` |
| 被动升级前置 | 同一玩法说明、`WeaponModule`和两版 `_refreshPassiveSkills` 均检查：第二个起的被动升级前，前一个被动达到 `WeaponConf.passiveLimit=10`；这是升级条件，不是永久开放条件 |
| 开放成功判据 | `WeaponModule._onSyncRoleBefore` 从服务器 `role.lordWeapon` 增量中的 `passiveSkill` 识别新开放被动并提示。辅助程序以完整角色查询中实际存在对应被动为准 |

**客户端能证明永久开放门槛、没有额外激活按钮，以及装配生效要求；不能证明服务端准确在哪个请求/推送时刻执行解锁。** 实现会先激活并装配皮鞋，再临时上阵满足条件的高星武将，并按官方进入界面的流程发送 `lordweapon_get`，最后查询角色。如果对应被动仍未出现，报告“触发条件待核实”并恢复默认阵容，不虚构成功、不发猜测的激活请求、不尝试打一次战斗或额外消耗。真实触发时机和线上完整返回体仍需实际账号响应补充验证。

## 实际指令与响应

当前协议注册列表为 `LordWeapon { changeDefaultWeapon:T, claimOpenReward:S, exchange:T, get:T, reset:EJ, unlock:T, upgradeActiveSkillLevel:T, upgradePassiveSkillLevel:T }`。
注册器使用 `(serviceName + "_" + method).toLowerCase()`，同时核对指令枚举：

| 指令 | 请求参数 | 客户端声明响应 |
| --- | --- | --- |
| `lordweapon_get` | `{}` | T=`SyncResp`，角色增量 |
| `lordweapon_claimopenreward` | `{}` | S=`SyncRewardResp`，角色增量与奖励 |
| `lordweapon_unlock` | `{weaponId:2}` | `SyncResp` |
| `lordweapon_changedefaultweapon` | `{weaponId:2}` | `SyncResp` |
| `lordweapon_upgradeactiveskilllevel` | `{weaponId:2}` | `SyncResp` |
| `lordweapon_upgradepassiveskilllevel` | `{weaponId:2,skillId}` | `SyncResp` |

不将增量缺字段当作清零。每次领取/激活/装配/升级后单独查询本账号完整角色，以领取记录、玩具存在、装配编号或技能等级确认；请求超时若查询已生效则继续，否则停止且不重发。

## 实现与使用

沿用批量、小号及定时共用的“自动升级皮鞋玩具”，不增加任务入口。页面提示补充临时换阵和恢复规则。

1. 查询当前账号配置版本，按官方加载器读取该版本 `configc.bin`；普通 `config.json` 不含玩具表，不能据此认为配置不存在，也不能回退到旧版本门槛。
2. 主公达到配置要求的4001级后查询玩具；礼包尚未领取则单独领取，刷新领取记录后再使用扳手激活皮鞋。
3. 确认装配皮鞋；主动升级读取**当前等级行**的 `activeCost`，到资源不足或满级为止。旧公式容易在30→31等突破边界偏移，运行流程已改用配置。
4. 按已拥有武将的实际星级选择最多5名最高星武将，同星优先保留在阵武将和站位。只在存在当前阵容尚未满足、但候选阵容可满足的未开放被动时临时换阵；不足的档位显示差多少星，不自动升星、不合成武将。
5. 复查实际阵容星级，查询玩具并确认新增被动；按配置检查前置被动等级、精铁、金币和上限，逐次升级并刷新库存。已开放被动不因当前星级下降而当作锁定。
6. 玩具已准备可升级后，正常完成、失败或停止均在清理阶段调用现有 `adjustMainLevelFormation` 并校验位置。默认为107、110、104、106，最后优先223否则204，只使用已拥有武将；不执行武将培养、资源回收或宠物调整。皮鞋保持装配以使被动生效。
7. 临时换阵途中停止也尝试恢复；恢复不受停止标记影响。连接断开等原因导致恢复失败时明确报错，不将账号标为成功；清理后才释放连接。

代码：`src/utils/shoeToyRunner.js`、`src/utils/batch/tasksItem.js`、`src/utils/xyzwWebSocket.js`。

测试配置样本 `test/fixtures/shoeToyConfig.json` 仅提取当前公开配置中的相关列，无账号信息，不用于运行时回退。
