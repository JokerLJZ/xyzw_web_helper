# 自动盐场快照缺失：接口核查与修改方案

调查日期：2026-10-25。范围：核查用户日志中的进场失败并给出修改方案；首次交付为调查方案；用户随后授权实施，修改结果见第7节。未使用账号连接或执行线上操作。

## 1. 结论

日志中的“盐场快照缺少本人或地图信息”是本项目 `SaltWarSession.enter` 主动抛出的本地异常，不是服务端原文。触发条件为以下任一项：`battlefield.roles` 不存在、`battlefield.buildingData` 不存在、`selfCodeId` 为假值。它发生在 `war_enterbattlefield` 返回并合并以后、布阵和行军以前。

已复现一处确定缺陷：合法模型中的空集合省略没有恢复。相同模拟快照在返回 `roles: {}` 时可以生成 watching 本人；只删除这个空字段就报用户日志中的错误。官方先创建协议模型，其 `roles`、`buildingData`、`legions` 等默认是空 Map；本项目直接消费 BON 原始对象，未恢复战场模型的集合默认值。现有测试只覆盖“显式空集合”，没有覆盖“整个集合字段省略”。

但用户没有提供进场原始响应，不能断言两个账号都由此触发：本人映射缺失、建筑缺失、响应被错误解包或场次不匹配被丢弃也会表现为同一条日志。应同时修复模型恢复和诊断，不能删掉检查后盲目攻击。

## 3. 正确流程与当前实现对照

| 步骤 | 已核对接口及参数 | 项目处理建议 |
| --- | --- | --- |
| 查入口 | `legion_getbattlefield {}`；联赛客户端另走 LeagueService | 每账号独立读取场次和资格，维持普通地图范围 |
| 连接 | 按 sid/domainName 决定主连接或专服 | 保留现有 sid2 路由、连接数限制和 war_ 的 hint |
| 进入 | `war_enterbattlefield {battlefieldId,useGzip}` | 先解析、核对场次，再恢复首次模型默认值，合并通知；当前就在这一步之后失败 |
| 身份确认 | 本账号主 roleId → roleMap.cId → roles 中本人 | 有映射才确认编号，不把其他人的 roleCodeId 推送当成本人 |
| 未出战初始化 | watching 展示角色 | 仅在身份和军团可核对时建立临时本人；不凭空补 energy、idle 或已出战状态 |
| 保存/出战 | `war_teamsetbattleteam` / `war_setbattleteam`，参数均为 battlefieldId、位置→英雄ID Map、lordWeaponId、petUId | 保存不等于出战；仅在确认 watching 且符合资格时执行，等待本人进入有效状态 |
| 核对阵容 | `war_getteaminfo {battlefieldId,roleCodeId}` | 确认返回 teamInfo 与本人状态，再允许移动 |
| 行军 | `war_startmarch {battlefieldId,target:{x,y}}` | 依当前地图合法路径选点，等待实际到达 |
| 加速 | `war_speedup {battlefieldId,marchId}` | 检查本人 march、剩余时间、队伍人数、服务器常量和预算；超时先查状态 |
| 攻击 | `war_startattackbuilding {battlefieldId,buildingId}` | 到达后重新核对归属、守军、争抢和体力，保持一次攻击限制 |
| 结算 | `war_endattackbuildingnotify` | 核对场次、本人、地块和 battleId 后确认结算；发起成功不等于结算成功 |
| 保活 | `war_ping {battlefieldId}` | 沿客户端已参战状态保活，清理本次拥有的连接 |

上述实际指令均有当前 Service 注册支持；不是按方法名单独猜测。下游流程仍须受本人的真实增量状态约束，不能通过修复进场校验绕过已有预算及防重逻辑。

## 4. 建议修改顺序

### 第一项：分离首次快照、增量与执行条件

修改 `src/utils/saltWarSession.js`：

1. 保留缺失、显式 null、空集合和非空集合的区别。只有首次成功进场快照按当前模型恢复可省略的集合字段；后续增量仍保留旧字段、按明确 null 删除条目。地图版本、状态、身份缺失不一概补成“可执行”。
2. 将 `enter` 中单一三项判断拆为：响应解析成功 → 场次一致 → 初始化状态容器 → 确认本人映射 → 初始化本人 → 执行前校验。不要在 watching 本人生成前因 `roles` 原始字段缺失直接退出。
3. 本人身份以该账号 roleMap.cId 为主。仅凭进场 response.roleCodeId 的回退需要补核对，尤其不能让广播响应抢先决定本人；映射和本人冲突时停止。无映射时不擅自认定 cId=主 roleId。
4. 现有主 roleId 与 cId 相等、军团可核对的 watching 兜底可保留并覆盖省略空 roles 的情况；匿名编号缺本人条目时先只读补查，不能未经证据任意合成本人的可操作身份。
5. 建筑集合恢复为空只表示数据容器可建立。建筑为空或关键地图数据缺失时，不允许选目标、行军或攻击。不能添加虚构的可攻击建筑；官方 0_0 仅为展示兜底。
6. 已解析但仍不完整时，节流后最多补查一次 `war_getbattlefieldinfo`，等待已排队通知完成后再校验。该查询声明只含 battlefield/battleList，不保证返回 roleMap；本人映射仍缺失就明确停止，不无限补查或反复进场。

### 第二项：补充可定位的脱敏日志

分别报告“未取得战场对象”“战场ID不一致”“本人映射缺失/冲突”“本人条目缺失”“建筑数据为空/缺失”“解压/解码失败”，保留服务端明确错误码。

建议记录阶段、请求命令、响应命令（需要传输层保留）、响应顶层字段名、是否压缩、集合字段是否存在及数量、是否命中本人映射、场次是否一致、是否做过一次补查。只记录必要的结构信息；不输出 Token、URL查询参数、完整玩家表、昵称或全量战场响应。本人具体ID可省略，使用“映射命中/未命中”即可。

当前 `sendWithPromise` 主要返回解码后的 body，通知订阅能保留 cmd。若需要判断压缩响应类型与请求响应归属，应明确传递包元信息，不用猜测业务 body 中不存在的字段。进场响应的解包、解压和订阅/Promise 去重需要一起回归。

### 第三项：保持写入确认与失败保护

进场阶段不写入“已攻击”，不消耗金砖。进入成功后也必须等真实出战/阵容确认，不能把临时 watching 角色当作 idle。出战、加速或攻击结果不明时仍遵循已有场次记录并先查询，不能自动重发。修复不要求用户清空场次记录或浏览器存储。

## 5. 回归与验收

建议新增以下有意义的测试后再修改实现：

- 显式 `roles:{}` 与省略空 roles 在同一合法身份场景中具有相同进场结果；同时覆盖普通和 deflate+BON 响应。
- 省略集合字段可建立初始容器，但 buildingData 为空不能触发行军/攻击；完整 battlefield 缺失不能伪造开战状态。
- 有映射、有本人；有映射、无本人；映射缺失；映射冲突；主ID与cId不同；多人进场广播与本账号进场响应交错。
- 首次默认 watching、后续省略 state 保留 idle；删除条目不因补默认值重新出现。
- 快照与通知乱序、一次补查成功/仍不完整/错误/停止；请求间隔至少500ms，不循环查询。
- 每种失败均明确指出缺失项，且不布阵、不行军、不加速、不攻击；日志不含认证信息。
- 批量一个账号失败不影响后续账号；定时入口复用同样处理并正确释放连接。

本次执行现有 `test/saltWar.test.js`、`test/tasksSaltBattle.test.js`：48项通过。另在临时脚本中对照同一模拟响应，确认“显式空roles → watching”“省略空roles → 本地报错”的差异；不是实际服务端抓包。现有48项通过不能证明本次现场已修复。本次仅文档调查，未修改业务代码，未执行生产构建。

上线验收先以一个账号只读进入战场并检查脱敏结构日志，确认具体缺失分支；再按已选预算验证出战、行军及一次攻击。拿到实际响应前，不把任何模拟数据描述为服务器真实返回。

## 7. 2026-10-25：已实施修复

- `saltWarSession.js` 首次建立战场对象时补齐当前模型的集合默认值；后续增量继续保留字段、删除明确null条目，不重置已出战状态。真实本人条目出现后清除临时watching展示，被删除后不回退到旧展示。
- 本人编号仅依据该账号roleMap，不再用任意进场报文的roleCodeId兜底。匹配请求的进场响应编号用于一致性检查；补查才取得映射时也重新核对。映射冲突立即停止，匿名编号无真实本人条目时不猜测。
- 省略空roles且已确认主ID映射和军团时允许建立watching本人；建筑为空、本人缺失或没有战场对象时至少间隔500ms只读补查一次，仍不完整就失败，不发送布阵、行军、加速、攻击指令。
- 失败日志区分未取得战场对象、本人映射缺失、匿名本人条目缺失、建筑为空或缺失、场次不匹配、身份冲突及解压/解码失败；缺失诊断附带初始字段是否省略、压缩标志、集合数量与补查状态，不输出角色表、ID或认证数据。
- 新增覆盖普通/压缩省略字段、匿名身份、映射冲突与补查后冲突、空建筑、通知补全、错误场次及广播干扰、停止、补查错误、损坏压缩数据和删除后不恢复watching。现有批量账号隔离、失败清理与定时入口回归一起验证。

最终测试与生产构建结果记于CHANGELOG本条更新。未操作真实账号，仍需用实际进场响应验证原日志对应的缺失分支；不能将离线模拟等同于在线攻击成功。
