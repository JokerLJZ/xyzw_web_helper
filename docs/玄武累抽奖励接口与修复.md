## 客户端证据

累抽界面 _renderTier 使用 cumulativeNum 判断门槛，点击调用 _data.sendClaimCumulative(o.id)。NewLotteryData.getCumulativeTiers(actId) 从 CumulativeDrawConf.list 按 actId 筛选；isCumulativeClaimed 按 cumulativeClaimedMap 的真实ID判断。sendClaimCumulative 调用 ActivityService.claimLotteryCumulative({id})，成功后更新 rawData.lotteryInfo。当前协议资源注册列表包含 claimLotteryCumulative，项目已有命令 activity_claimlotterycumulative 及对应响应映射，本次未改变命令。

配置 JSON 的实际表名是小写开头 cumulativeDrawConf（先前只按大写查找导致遗漏）。data/da6870e190/config.json 含134条记录；旧活动2609192的前3档ID为1、2、3，本期2611132的前3档为68、69、70，门槛分别为5、10、15。累计16抽且未领时应选择68、69、70；不能发送旧活动ID1。

## 实现

每个账号执行时通过 system_getdatabundlever 查询配置版本，动态加载配置，使用已解析玄武活动日期前缀加2作为抽奖活动ID。按配置门槛排序，仅请求达标未领记录，不再硬编码1至20。没有当期配置则说明错误并停止，避免猜测ID。

领取响应没有 lotteryInfo 时再查询；只有对应领取记录明确为true才计入成功。同次任务保存确认过的ID，避免后续循环重复领取。失败或无法确认时阻止本次任务后续重试；下次任务重新查询状态。保留请求间隔及原抽奖安全上限。未连接真实账号，当前服务端成功响应结构尚未实测；状态无法确认时宁可停止，不推测成功。
