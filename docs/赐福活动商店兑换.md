# 赐福活动商店兑换

## 使用

批量日常任务 → 一键玄武赐福旁的“赐福活动商店兑换”。打开时读取公共商品清单，不连接账号；选择商品的每账号兑换份数，查看预计消耗后点击批量兑换。默认所有份数为0，不随一键赐福自动兑换。

按商品展示顺序逐账号执行，执行前重新读取账号库存、兑换记录与当前配置。库存不足、达到限购或未解锁时跳过对应物品并记录原因，继续处理其他选择。写请求超时或兑换记录未确认时停止该账号且不自动重发。一次只选择一个商店；切换商店清空已填数量，活动/配置切期需重新打开清单。

## 当前客户端证据

2026-11-13重新读取 public/game/index.html 指向的 game-defines.a175e.js 和 main.2a00e.js 加载链，按其POST manifest参数 platform=hortor、version=0.36.0-android取得 game=03828、launcher=c3d60、TEST_REMOTE_MODULE=66a37、dataBundleVer=da6870e190，COMMIT_ID=8a028b80。按convertAssets规则从remote下载当前脚本，复用启动器纯XXTEA解密函数分析，没有运行下载业务脚本。

- FestivalExchange界面 → getExchangeConfig / ExchangeActConf，consumeNum为每份价格，limitNum为限购，unlockNeed为累计消耗要求。FestivalData.consumeAmount按本商店已兑换记录乘价格求和。
- FestivalModule初始化Exchange与Exchange_2均从ExchangeActConf选择本活动商品，消耗道具从ActFestivalConf.itemId读取。不得固定旧玄武道具5285。
- shouldShowNewExchange2Entry明确要求同组GACHA_2已结束；本功能据此在抽奖结束后才列出Exchange_2商店。
- FestivalModule.sendExchange(activityId,goodsId,quantity) → ActivityService.exchange({activityId,goodsId,quantity})；当前协议资源注册列表包含exchange，字符串表含activity_exchange；项目现有CommandRegistry与奖励响应映射已支持该指令，本次直接复用。
- activity_get返回的activity.commonActivityInfo[activityId].record保存商品兑换份数；role_getroleinfo查询该账号items。兑换后再次查询record增长作为成功依据，不依赖写响应必须带reward或完整角色信息。

当前配置主活动为凤仪祈愿（GACHA_2=35），同组同期主商店2611133（Exchange=2）用5297灼华赤羽，共30种商品；第二商店2611136（Exchange_2=34）用5296，共9种商品。主商店前一项261113301为5赤羽兑换白玉5000、限购10。两种商店结束时间可晚于抽奖，故按各自有效期判断，不要求抽奖仍开放。

应用按GACHA_2配置确定活动组和开始时间，再选择相同组与开始时间的2/34商店，避免硬编码本期日期、商品ID和货币。只对所选商店、商品与份数发请求。

## 实现与验证

blessingShop.js负责识别、公共清单与商店绑定；复用rechargeActivity.js的库存/限购/解锁判断及写后确认、tasksRecharge.js的批量连接管理、RechargeExchangeDialog.vue的商品选择弹窗。入口仅增加到批量任务页，不新增默认自动消耗或定时兑换任务。

新增8项回归覆盖阶段开放、到期、公共清单、账号隔离、解锁与限购、精准请求、超时与未确认后不重试、跨商店与非法份数。全量1068项测试及临时目录生产构建通过，保留既有构建提示。实际读取当前官方公共清单，确认商品名称、价格、数量与货币显示；没有执行真实账号兑换，成功响应仍以首次实际使用验证为准。
