# 日常任务判定逻辑核查与修改建议

分析日期：2026-10-18。应用户要求，本次只调查、列问题及建议，没有修改功能代码，也没有执行真实账号任务、领奖或推送。工作区已有上一轮未提交修改；本报告以这些修改后的当前代码为审查对象。

## 一、先回答周活跃未达档位的问题

当前官方配置：日活跃20/40/60/80/100，周活跃100/200/300/400/500。

当前游戏 DailyTaskModule 中 TaskChainData.setPoint 只有在 `item.point <= curPoint` 且未领取时才将档位设为可领取；已领取记录由 setRewardState 标为已领。FullTaskContainerDialog 的单档位仅在state=1时调用领取；总领取按钮也先检查红点。

项目 getClaimablePointRewards 也只筛选 `points >= reward.limit && claimed[reward.id] !== true`，最终 remainingRewards 同样只统计这些可领奖励。直接使用当前配置验证：周分0/99没有可领档位，100/150只有第1档，499有第1至4档，500有第1至5档。因此“积分不足本身会导致失败”目前未被代码或这次验证证实，不能据此取消领奖核验。

但是缺省字段、旧状态、错误分类及日志确实有下述问题，可能让正常不能领取变成异常。用户尚未提供一份明确包含周分、周奖励记录及对应失败响应的日志，无法给某个账号的失败定唯一根因。

## 二、问题、依据及建议

| P2 | 步骤返回状态没有统一处理，梦境异常可能显示已处理 | 通用循环只特殊识别status=skipped和字面false；dreamTaskRunner的正常结束与异常结束都可能返回status=stopped，异常另外带pushError。runDreamTask原样返回，外层会计作completed。其他skipped:true结构也只计已处理。 | 明确定义正常停止、条件跳过、失败、结果未知四种结果；优先检查pushError等异常字段，不把“吕布无法继续”和“网络/业务异常”一概处理。统一结构后再决定是否阻塞计划完成。 |

## 三、已核对符合游戏依据的部分

- 官方任务id与completeCondition分开映射；当前竞技场任务id=8、条件=13，没有混用。
- 完成进度达标与任务积分已领取分开判断；当前任务-1标记为已领，达目标但未领还需task_claimdailypoint。
- 日/周活跃只领已达标且未领档位，积分低于下一档不计入remainingRewards。
- 最后重新读取服务器角色核对，而非只因请求成功就报领奖成功。
- 3500020只在通行证activity_recyclewarorderrewardclaim中按无奖励跳过；200020没有统一当作正常跳过。超时仍先查询且不盲目重发。

## 四、建议修正顺序

1. 先统一结果定义及展示：未达标/已领/关闭/未开放为正常跳过；该领未领为待继续；明确异常和状态未知分别展示。分开“游戏日常完成度”“当前执行计划完成度”“附加任务提示”。
2. 处理可信完整快照的模型默认值和日/周同步，再核对周活跃边界；保留真实异常，不放松所有字段校验。
3. 修复服务器时间和竞技场边界，落实用户开关对本轮完成判定的影响。
4. 按官方Module逐项补固定奖励、免费次数、梦境等步骤的前置条件和结果验证。
