# 批量任务连接失败后自动重新获取 Token

## 现象与定位

用户日志表现为首次连接等待10秒，随后“尝试重连”，再次等待10秒后失败；到 Token 管理页面重新获取 Token 后连接恢复。

代码确认的差异：

1. BatchDailyTasks.ensureConnection 的重试只是从本地 tokens 再读一次同一个凭据，不会调用 URL 来源或用保存的 BIN/扫码原始数据重新登录。maxRetries 仅判断是否大于0，因此配置2次实际只执行一次。
2. Token 管理页面的“刷新/重新获取”会通过来源 URL 获取 token，或调用现有 transformToken，以 IndexedDB 中的 BIN/扫码数据重新获取登录凭据。
3. Token Store 自带的后台刷新只在部分握手失败、Token expired 消息等条件下触发；纯超时不保证触发。它还可能与任务页重试并发，而且旧 WebSocket 回调未校验连接归属，旧断开事件可能覆盖新连接状态。
4. 旧异步关闭没有在批量重连前等待完成；握手未完成的连接被关闭时，还可能留下 connect 锁，影响下一次创建。

因此用户现象与“旧凭据重试未刷新”的路径一致；没有用户当次握手报文，不能仅凭超时日志断言所有失败都是 Token 过期。

## 修复后的行为

- 首次连接正常使用当前 Token，成功则不刷新。
- 首次连接失败后先等待旧连接关闭。账号有 URL 来源，或导入方式为 BIN/扫码时，本轮最多重新获取一次凭据，再使用当前账号最新存储记录重连。
- maxRetries=2 表示首次连接加最多两次重试。刷新失败时明确提示到 Token 管理检查来源或重新导入，不继续使用原凭据反复重试。
- 手动导入且没有自动刷新来源的账号保留有界连接重试，并明确提示失效时需要重新导入。
- 检测到连接 error/disconnected 时尽早进入恢复流程，不无条件耗尽整个等待时间；等待连接、刷新后及延迟后均检查停止请求。
- URL 来源禁止缓存，15秒请求超时；沿用 authuser 全局限流。BIN/扫码沿用 transformToken 的限流登录流程，登录网络请求增加15秒超时。限流排队时间独立于网络请求超时。
- 凭据刷新独立于建立连接和选择账号。任务调用不会切换页面当前选中账号，也不会由刷新入口额外创建连接。同一账号并发刷新共享进行中的请求，账号之间相互隔离。
- 用户刷新期间手动更新或移除账号时，不把旧刷新结果写回覆盖。旧名称键存储的 BIN 会在成功读取后迁移到账号 ID，保存失败时保留旧数据。
- Token 页手动刷新与后台自动刷新共用同一个凭据刷新实现；其他手动重新导入流程保留。
- 批量连接关闭 Store 的握手自动刷新回调，统一由任务页控制次数和凭据，避免两条恢复路径竞争。
- Store 的连接、错误、断开及消息回调校验当前 client 归属。旧连接事件不更新新连接，也不释放新连接持有的锁；主动关闭不触发握手自动刷新。重连前释放失败连接锁，内部替换连接时保留正在创建的新连接锁。
- 重试不重复取得连接槽位；最终失败或停止由外层 ensureConnection 清理本次连接并释放一次槽位，保留定时账号会话原有约定。

本次没有新增或改变游戏业务指令、authuser 请求地址、请求体或登录参数，只复用项目已有的凭据重新获取路径并增加网络超时。未调用真实账号进行登录或任务消耗验证。

## 实现与验证

- `src/utils/tokenCredentialRefresh.js`：独立的凭据刷新及同账号并发去重。
- `src/utils/batch/connectWithTokenRefresh.js`：等待关闭、刷新一次、按次数重连与停止处理。
- `src/stores/tokenStore.ts`：提供凭据刷新/异步关闭方法，隔离旧 client 回调。
- `src/views/BatchDailyTasks.vue`：接入连接恢复和明确日志。
- `src/views/TokenImport/index.vue`：手动刷新共用 Store 方法。
- `src/utils/token.ts`：authuser 网络请求超时。

测试覆盖 URL/BIN 刷新、旧键迁移、无来源/原始数据缺失、同账号并发去重、账号移除/手动更新竞争、刷新失败后重试、新凭据重连、准确重试次数、停止、连接锁释放及迟到回调隔离，并回归批量槽位清理。

若没有保存的 BIN/扫码原始数据，或来源服务本身无法返回有效 Token，仍需在 Token 管理重新导入。测试与构建结果记入 CHANGELOG.md；服务端对本次失败的确切原因仍需实际握手/登录响应确认。
