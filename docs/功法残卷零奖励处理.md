# 功法残卷领取零奖励处理

分析及实施日期：2026-10-24。

## 客户端证据

复用同日从本地 `public/game/index.html` → `game-defines.a175e.js`、`main.2a00e.js` 追踪取得的当前公开资源，未使用账号。manifest 为 POST `/login/manifest?platform=hortor&version=0.36.0-android`，空请求体；清单 COMMIT_ID `7c1732a0`，codeVersion `2.51.5`，game `d8db3`、launcher `cd44d`、协议 TEST_REMOTE_MODULE `c501f`，dataBundleVer `58b91ed6c8`。原始资源、解密代码和配置位于临时目录 `/tmp/xyzw-iron-20261024/`。

UI 的 `m_exploreComp.m_btnClaim` 检查探索开始时间距服务端当前时间是否达到 `LegacyConstant.minDreamDustCollect`，当前配置为60秒。`LegacyModule.sendClaimHangUp` 调用 `LegacyService.claimHangUp({})`；成功后将完整 `reward` 列表交给奖励弹窗，并不直接读取第一项或要求响应包含库存总量。协议注册列表存在 `claimHangUp:bP`，项目既有指令为 `legacy_claimhangup`、空参数；本次未完整解混淆协议注册器和bP模型，也未取得真实账号响应，不推断缺失字段意味着零库存。

界面预估数量来自探索耗时、LegacyDreamDustConf.produceSpeed 与探索时长上限；produceItemCnt不是直接的当前可领数量。当前实现使用WebSocket客户端同步的服务器时间计算产出，不使用本地日期时钟，不把任意服务端错误认定为无奖励。

## 领取前判断（按用户补充要求实施）

先按账号查询当前配置版本并加载官方config.json，再发送 `legacy_getinfo` 取得该账号的roleLegacy。以 `hangUpBeginTime`（毫秒）、`produceLevelId`、对应配置的 `produceSpeed`（毫秒/份）和WebSocket客户端的 `getServerTime()` 判断是否产出至少一份。尚未开始探索或已产出数量为0，直接completed并记录跳过，**不发送 `legacy_claimhangup`**。达到一份且满足 `minDreamDustCollect` 才发送领取指令。查询失败、状态字段/配置/服务器时间无效时不猜测数量，保留失败。

官方显示数量为 `floor(clamp(serverTime-beginTime, 0, maxTime)/produceSpeed)`，maxTime为基础时长加特权延长。此处只判断是否至少一份，验证基础上限已足够产出一份后，特权延长不会改变零/非零结果，因此无需推测账号特权或请求额外特权状态。`produceItemCnt`是产出等级进度，不能直接当作可领取数量。

配置复用现有按版本缓存的 `loadSignupCheerConfig`；配置版本从该账号 `system_getdatabundlever` 读取。保留空奖励响应处理，防止判断与请求之间状态变化造成误报；不增加服务端错误兜底。

## 项目修改

原批量领取代码直接读取 `reward[0].value` 和 `role.items[37007].quantity`，空奖励或不带库存的成功响应会在日志拼接时抛异常。

现改为按物品ID37007统计残卷奖励：空奖励列表或残卷数量为0时，信息日志提示正常结束，账号标记completed；有残卷时显示实际数量，只有响应带库存总量才显示总量。真实请求异常、缺失奖励列表或无效奖励数值继续失败，不重试。没有添加服务端错误码兜底或新增线上写操作。
