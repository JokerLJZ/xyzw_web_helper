# 自动盐场：进场、布阵、最近地块与一次攻击

调查与实现日期：2026-10-17。第一版已接入批量与定时任务；未使用真实账号连接战场、布阵、加速或攻击。以下保留机制证据与初始规划，实际实现和验证见文末。

## 1. 结论与建议范围

能够实现，但需要专门的战场会话、地图寻路和状态确认，不能只在现有任务中串行发送四条指令。

建议第一版命名“一键盐场参战一次”：读取该账号当期战场，进入战场视图，使用指定阵容出战，寻找最近的合法可攻击地块，行军并在预算内加速，到达后发起一次地块攻击，确认该次结算后结束。这里“攻击一次”是一次攻城战，不是占领一块地，也不保证占领成功。

默认目标为非己方、非主城、当前开放且可达的地块；优先没有守军和敌对争抢、可直接攻击城防的目标。没有符合条件的地块时明确跳过。第一版限定普通盐场；联赛、夺旗、决战盐山等地图有独立规则，不能未经适配直接套用。

## 3. 实际操作机制

### 战场入口和连接

LegionWarModule.sendGetBattlefield 调用 LegionService.getBattlefield（联赛另走 LeagueService）。_onGetBattlefield 读取 info.battlefieldId、phase、readyTime、startTime、endTime、canEnterWar、sid、domainName，以及 isInWeekWar / isInMonthWar 等资格信息。

LegionWarNetworkData.setSId 决定连接方式：sid 非空时建立专用 WebSocket，并在连接参数添加 sid2；domainName 非空时使用返回域名。sid 为空时复用主连接。客户端发送器仅把 war_ 指令切换到战场连接，其他指令仍走主连接。因此不能写死盐场服务器，也不能把所有战场指令无条件发到普通角色连接。

enterBattlefield 请求只是进入并取得战场数据，未必已经出战。玩家可能处于 watching；仍需布阵、提交出战并确认 idle 等状态。客户端区分 idle、ready、started、ended 战场阶段，不能把本项目“周六报名”限制当成实际参战时间。

### 布阵与出战

LegionWarDeployDataAdapter 默认从 ROLE.battleTeam 提取位置→heroId，可使用盐场已有保存阵容；保存路径为 LegionWarDeployData.dealDeploy → teamSetBattleTeam，实际出战按钮则走 sendSetBattleTeam → setBattleTeam。

请求中的 battleTeam 是位置到英雄ID的数字 Map，另带 lordWeaponId、petUId。不能把主线完整武将对象直接塞入，也不能漏掉玩具和宠物。LegionWarPanel._onClickDeploy 检查 isLeader、teamLimitTime、svrTeamingTime；组队成员不能被当作独立队长任意移动。第一版建议仅处理单人队伍，遇到多人队伍明确跳过，避免影响其他玩家。

### 移动与最近地块

LegionWarBuildingPanel._onBtnAttack 在未到目标时调用 sendStartMarch(building.position)。参数是目标坐标 {x,y}，不是 buildingId，更不是整条路径。

canMoveHero 要求本人 idle，不在该地块或该地块行军中，目标不受相应保护期或关闭限制，地图未锁定，且 navPath 非空。

SourceMap.navPath 使用 TMAStar2.AStar；地图是按 x 奇偶切换邻接方向的六边格，非普通八方向网格。地图 Data/Building 图层、地块归属、盐田中心及周围格、跨敌方地块数量均会影响通行。navPath 对途中敌方地块数量有额外限制，联赛子类还会增加封锁与特殊路线规则。

“最近”应按合法路径长度排序，同路长以预计行军时间、可攻条件和稳定地块ID作确定性排序，不能按坐标欧氏距离选点。地图地形需沿当前 TMLoader/ResourceManager 的地图资源加载链取得；配置表 LegionWarCityConf 只有名称坐标，不能代替完整可通行图层。最初调查时尚未解析地图；实现阶段已补齐当前启用普通地图的解析与验证，见第7节。

### 加速

sendSpeedUp 要求 march 状态、使用实际 marchId、剩余行军时间达到 legionWarMoveTimeLowerLimit × moveTimeScale，并通过 canSpeedUp 检查。客户端加速发送节流为约2秒。

canSpeedUp 使用“legionWarSpeedCost × 队伍存活人数”检查金砖。本次 ConstantConf 的基础值为 speedCost=20、speedRate=50、moveTimeLowerLimit=10秒、moveTime=25秒。战场 getConstValue 优先用服务器下发 constant，再回退配置；部分联赛阶段 moveTimeScale=0.5。因此数值只能作为当前基础参考，运行时不能固定每次20或认为一次加速立即到达，speedRate 的实际剩余时间变化仍应以返回的 marches/endTime 确认。

建议第一版最多加速一次，提供每账号金砖上限；不满足最低剩余时间时直接等待，预算或余额不足时按用户设置等待或跳过。主角连接的通用心跳不能代替客户端战场 war_ping。

### 攻击地块

到达后必须重读该地块与本人状态。_canSelfDig 要求本人 idle、在攻击方列表、地块剩余城防可攻击。canAttackBuilding 还要求仅有一方可参与攻城的攻击军团、无有效阻挡守军；剩余城防还会扣除已经排队占用的攻城战。

因此“到地块了”不等于“可以攻击”。守军、多人争抢、地块易主、保护期、城防已被其他战斗占用，都可能阻止攻击。客户端有对玩家挑战、额外攻击、自动攻击、自杀复活等其他路径，第一版不启用这些路径：本任务只做一次标准地块攻击。

_onStartAttackBuilding 合并 battlefield 并登记 battleInfo；_onEndAttackBuilding 通过 battleId 移除战斗并合并新状态、处理城防和归属变化。收到发起响应只能记录“攻击已发起”；收到本人、目标、battleId匹配的结束通知或等价查询证据后，才能记录“本次攻击已结算”。

## 4. 已确认接口

协议资源中 Service 注册器 _gs 以 (serviceName + '_' + method).toLowerCase() 注册命令；War 注册列表明确包含以下方法，协议命令常量同步存在。

| 步骤 | 实际命令 | 参数及依据 |
| --- | --- | --- |
| 查询入口 | legion_getbattlefield | {}；LegionWarModule.sendGetBattlefield，项目现有报名任务亦使用此指令 |
| 进入战场 | war_enterbattlefield | {battlefieldId, useGzip}；sendEnterBattlefield，普通与gzip响应分开处理 |
| 查询战场 | war_getbattlefieldinfo | {battlefieldId}；sendGetBattlefieldInfo |
| 保存阵容 | war_teamsetbattleteam | {battlefieldId, battleTeam, lordWeaponId, petUId}；dealDeploy / sendSetTeamBattleTeam |
| 提交出战 | war_setbattleteam | 同上；sendSetBattleTeam、Panel._onClickDeploy |
| 行军 | war_startmarch | {battlefieldId, target:{x,y}}；BuildingPanel → sendStartMarch |
| 加速 | war_speedup | {battlefieldId, marchId}；sendSpeedUp |
| 攻击城防 | war_startattackbuilding | {battlefieldId, buildingId}；BuildingPanel → sendStartAttackBuilding |
| 战场保活 | war_ping | {battlefieldId}；sendWarPing，仅已参战且非观战时发送 |

声明模型中 EnterBattlefieldResp 有 roleCodeId、battlefieldId、battleList、roleMap 等，并继承战场公共响应；StartMarchResp 有 marchId、battlefieldId；SpeedUpResp 另含 role；StartAttackBuildingResp 有 buildingId、roleCodeId、battlefieldId、battleInfo。字段继承、默认值与通知增量不能被误当作完整快照。gzip分支先 inflate，再进行BON解码。真实响应省略字段的范围和推送顺序尚待受控在线验证。

## 5. 实现规划

1. **只读预览**：逐账号读取入口、场次、资格、阶段、地图类型、主线或指定阵容、加速预算。显示可执行/跳过原因，暂不自动报名。现有报名任务保持独立。
2. **战场会话层**：新增独立会话，按 sid/domainName 路由，支持普通/gzip快照、增量合并、状态通知、war_ping、断线重查。与现有账号连接池协调，不绕过并发限制，不破坏主连接与其他任务。
3. **地图与规则层**：按地图版本解析可通行图层，复现六边格与目标过滤规则，计算最近合法路线。第一版只启用核对完成的普通地图；未识别地图停止，不能靠坐标猜路线。
4. **动作状态机**：预检 → 进入战场视图 → 保存阵容/提交出战 → 确认idle → 选点 → 发起行军 → 按预算加速 → 等待到达 → 重核目标 → 发起一次攻城 → 等待结算 → 清理会话。已经在合法可攻地块时直接攻击；已经在行军或战斗中时先恢复状态，不重复布阵或另发动作。
5. **一次性与调度**：以账号+场次+战场ID记录待确认/已发起/battleId/已结算，持久化后再支持定时入口，重跑不追加一次攻击。预算按场次累计，超时查询确认，不盲目重发出战、加速或攻击。无法确认的攻击明确标为待核实，不能报成功或自动重新攻击。
6. **界面**：新增“一键盐场参战一次”和设置：阵容来源、加速次数与金砖上限、余额不足处理、最长等待时间。日志集中展示目标、路长、实际加速花费、攻击及结算结果。停止按钮阻止后续写入；已发出的行军和战斗由服务器继续，不承诺停止能撤销。

建议默认：复制该账号当前主线阵容，单人队伍，最近合法非己方普通地块，最多加速1次，金砖上限20且按实际报价检查，完成一次标准攻城后结束。上限低于当前费用时等待而非追加预算；不保证一定找到可攻目标。

## 7. 第一版实现与使用

批量任务页日常区域新增“自动盐场（一次攻击）”。先逐账号预览场次、本人状态、最近合法目标、路径格数和加速单价，再按设置执行。每账号本场金砖上限、0/1次加速、10～900秒等待均可设置，默认20金砖、1次、180秒。定时任务同名入口保存独立设置。

未出战时复制该账号当前主线位置→英雄ID、玩具、宠物，先保存阵容再提交出战，等待idle并用war_getteaminfo.teamInfo核对武将，配合本人快照核对玩具和宠物。已出战idle角色保留盐场现有阵容；多人队伍、其他行军或战斗跳过。本功能不自动报名、复活、自杀、攻击玩家或连续攻城。

### 地图解析与范围

实现阶段已经补齐初始规划中未完成的地图解析。saltWarMap.js按当前manifest下载Cocos bundle配置、解码UUID和导入版本，从TiledMapAsset提取TMX，解析data/building CSV图层和建筑类型。按照LegionWarMapTypeMappingConf识别普通地图，不支持的联赛、夺旗、预选赛、四象与决战盐山停止。最近按合法六边路线长度排序；己方盐田中心的周围格按客户端作为强制通行点。目标限定非己方、非主城、非中心盐田、已开放且无守军、争抢、排队战斗的普通地块，过滤比客户端手动操作更保守。

已实际下载解析当前启用资源：demoMap/403ed/legionWarMap，IntroMap_02/50be1/map01、map02、map03，IntroMap_03/98a89/map01，IntroMap_01/a79fe/map01，IntroMap_06/101da/map01，IntroMap_04/1fea9/map01，IntroMap_05/acb1d/map01。前者41×37，其余41×36。以上哈希为调查记录，代码动态获取，不硬编码这些版本。

### 会话、预算与一次性确认

saltWarSession.js根据sid/domainName选择主连接或独立WSS，保留认证与编码参数、附加sid2；war_报文带hint=battlefieldId。独立订阅不覆盖tokenStore监听，支持deflate+BON快照、增量保留与显式null删除、战场保活。逐账号串行处理，清理本次拥有的连接；专服同时最多1个，已有连接达到10时拒绝新增。

saltWarRunner.js每次写入前保存场次记录；写超时后查询且不自动重发。加速次数与预算在发送前预留，服务端constant.SpeedCost等枚举键优先于全局配置；预算、余额或时间条件不满足时自然等待。到达后重查本人位置、军团、体力、目标归属和成员/战斗队列，允许才发起一次攻城。只有本人、目标、battleId匹配且hP非负的war_endattackbuildingnotify才记为完成；取消的攻城不追加。

记录按账号+phase+battlefieldId保存于localStorage（xyzw:salt-once:<账号ID>），不含Token。通过Web Locks及页内账号锁防止并发。停止后阻止新写入并清理会话，已发出的行军和战斗不能撤销。已完成场次不再攻击，结果未明则保持pending。

### 限制与验证

当前没有预设阵容选择器，仅“未出战复制主线/已出战保留”。目标在到达后变为不可攻就停止，不另换目标继续消耗。断线或通知缺失时，不从当前idle或城防变化推断本人攻击成功；该场保持待核实，重跑不会绕过一次性限制。后续若需自动恢复，须依据真实战报接口补充确认，不能直接重发。

专项测试覆盖专服路由及失败释放、hint/响应匹配、订阅隔离、gzip、增量、地图版本查找、六边格与强制通行、资格及阵容核对、体力与预算、各写请求超时、停止、目标易主、结算缺失/取消、账号场次隔离、批量清理与定时预算。最终数量及构建结果见本次CHANGELOG。

本次未执行真实账号操作。上线后应先选一个单人账号、明确预算做受控验证；实际响应省略和推送顺序仍需核对，发现差异时保留脱敏响应再适配。

## 8. 2026-10-18：修复未布阵、空阵容及中断恢复

### 已确认的代码缺陷

当前协议GDBattlefieldRole构造器将state默认设为watching，lordWeaponId=0、petUId为空字符串。官方客户端先用模型还原字段，再由LegionWarPanel._onClickDeploy及LegionWarDeployData决定是否保存/提交出战。本项目直接消费原始BON，先前没有补回新角色省略的watching，导致未进入布阵分支。这是确定存在的路径，但没有用户本次响应体，不能断言为线上提示的唯一原因。

现在只对首次出现的角色条目按声明模型补默认值；已有角色的稀疏增量仍保留之前state，避免把idle错误重置为watching。本人身份继续依据roleMap[主角色ID].cId，不用其他玩家响应中的roleCodeId替换本人；已有watching展示也不跟随错误映射。

### 布阵、核对和恢复

- 未出战：复制该账号主线武将数字Map、玩具和宠物，保存阵容后提交出战；待idle后查询一次war_getteaminfo核对，未确认不移动、不花金砖。
- 已出战且有有效阵容：查询确认后保持原阵容，不再次提交出战。
- 已出战但阵容为空：按客户端右侧布阵按钮使用的teamSetBattleTeam恢复主线阵容，再查询核对；不重复setBattleTeam出战，修复未生效即停止。
- 日志及场次记录区分saveFormation、formationSaved、deploy、deployed：保存已确认且从未提交的出战可以继续；旧保存结果未知时只补查一次，确认后才继续。提交出战超时且结果未知仍不重发，不清除攻击和预算限制。
- 布阵/出战失败将指令、阶段、角色状态和明确服务端错误码保存在原场次记录中；阵容核对失败补充服务器阵容人数，后续无需仅靠临时日志才能定位阶段。记录不含Token或连接URL。
