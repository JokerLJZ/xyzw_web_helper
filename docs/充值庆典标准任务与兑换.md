# 充值庆典标准任务与兑换

## 使用入口

批量日常 → 副本：

- **充值活动标准任务**：按生日祝福及领奖 → 周年烧烤 → 活动道具抽奖 → 免费福袋及累计充值免费档的顺序运行。可在现有定时任务中选择同名任务；不会自行创建定时计划。
- **充值活动兑换物品**：直接打开公共配置生成的预设清单，无需逐账号查询。填写每账号兑换份数后批量执行；逐账号核对实际库存、解锁、已拥有皮肤及限购，份数不足或服务器明确拒绝时跳过该物品并继续。超时、记录未确认或切期仍停止该账号，避免重复消耗。份数不足时整项跳过，不擅自减少所选份数。

生日任务每天最多进行两次**具备领取条件的真实任务邀请**，已在当天完成的邀请计入上限。任务的首份奖励先领取，之后按具体任务 ID 邀请，再领取第二份。客户端每个累计祝福任务只允许两份奖励，所以第一天只有一项任务时，不发送没有可领奖任务的第二次邀请。主页面邀请按钮走 `sendCelebrationInvite(0,true)`，只是分享展示，不能用发送两次 id=0 代替完成任务。

烧烤每日 08:00～20:00（中国时区）可挑战。每日总次数为配置 `parameters[1]+1`（含免费首轮），开始新轮前保留3次。与“一键换皮闯关”共用执行器：胜利直接续战下一层，失败后才重新开始；不再要求每场 fight 后次数增加1。已开始的一轮可在剩余3次时继续免费续战，失败后不再开新轮。通关或连续5败跳过当前BOSS，跨日或超出时段停止。挑战前从该账号读取主线武将位置、玩具和宠物，以 teamType=6 同步闯关阵容并核验，不修改主线阵容。

狂欢抽奖每次10抽或1抽，仅使用配置中的普通活动道具。没有活动道具就结束，不用路路通兑换，不自动开启或选择进阶宝箱奖励。每次抽奖后重查该账号库存，必须确认扣除数量。

免费奖励包括周年商店零价格礼包及累计充值 `chargeAmount=0` 档。周年福卡属于付费权益：仅已购账号领取已有可领权益，不购买福卡、不发起充值。已领奖励不会重复领取。

## 复用设计与状态处理

每个账号先请求 `system_getdatabundlever`，按实际版本加载配置，仅缓存不可变配置。以 actConstantConf 当前活动组0、有效期和开始时间关联 ActFestivalConf，再按玩法类型定位子活动。下一次相同机制活动自动使用新 ID、新价格、新道具和新时间。缺少受支持的子活动则跳过该子步骤；未知机制不能自动视作兼容。

每个账号独立查询领取记录与库存，不共用 tokenStore 中另一个账号的选中角色状态。库存来自完整 `role_getroleinfo`，写响应中的 role 是可能缺字段的增量，不能将缺失库存当作0。每次写后重新查询状态确认；写失败/超时先尽力查询该阶段状态，不盲目重发或自动重试。兑换在结果不明时停止该账号的剩余兑换；标准任务保留错误日志后继续后续独立阶段，整体标记未全部完成。

时间优先读取该账号 WebSocket 客户端 `getServerTime()` 的服务器时钟，尚未获得时以本机时钟为暂时回退。连接走现有队列并在单账号间顺序处理，复用定时账号会话；只清理由本任务取得的连接槽位。

响应模型来自客户端声明，尚未取得真实账号本期返回体。缺失关键快照、库存、次数或写后确认失败时会停止对应操作，可能需要根据真实返回进一步兼容。本次未执行真实账号挑战、抽奖、充值、领奖或兑换。

## 2026-10-16：祝福响应与闯关机制修复

重新请求当前manifest并下载匹配资源，game=22c3b、launcher=861b5、TEST_REMOTE_MODULE=dcdf9、config=0c3a7d906d，与前次版本一致。没有使用真实账号执行布阵或战斗。

生日祝福：Celebrate_GetCelebrateInfoResp继承CelebrateInfo，后者默认创建GDSignCelebrate实例及空Map。原始BON返回省略默认字段时，原实现会误判“未取得生日祝福状态”。现在补回空实例、空Map和零计数，再执行祝福并查询核验；明确的null、数组和未知结构仍停止。签到同时检查客户端YYMMDD日期键，键存在但时间值为0也不重复签到。用户日志没有原始响应，因此默认字段兼容是客户端模型证明的修复路径，尚未取得该账号实际返回体。

闯关调用链：ActivityFestivalTowerDialogDelegate._startChallenge对正在战斗的塔直接sendFight；BingoBattleWinDialog继续按钮只调用sendFight；BingoBattleFailDialog._onClickContinue先sendStartTower再sendFight。这与原skinChallenge的needStart流程一致。现两入口共用状态机，烧烤仅增加保留3次和主线布阵参数。普通一键换皮不启用保留3次，也不额外复制主线阵容；保留原连续5败跳过当前BOSS的策略。

Towers_GetInfoResp/start返回完整ActGDTowers，fight.towerData则为单塔GDTowers，不能混为同一快照。胜利以层数、通关或新奖励标记核验，不再要求每场次数加1。次数以查询和战斗响应对账，本轮只增不减，避免写后查询暂时滞后导致重复开轮。写超时只查询，不重发开始或战斗；次数、结果或进度未确认时停止。

布阵：已核对Team服务getAllTeam/setTeam注册列表（均返回SyncTeamResp）和EMTeamType.level=0、towers=6。主线来源为该账号role.battleTeam、role.lordWeaponId、role.pet.petUId；保存后核验roleTeam.battleTeamInfo[6]、weapon[6]及pet[6]。不使用另一账号缓存，不修改主线本身。已在进行中的轮次仍按服务端续战状态运行，保存阵容用于该玩法后续开始的轮次。
